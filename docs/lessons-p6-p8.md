# P6-P8 Lessons（2026-06-19）

## 审批与审计必须分开处理敏感数据

- 审计记录应先脱敏，避免 Token、Secret 和 API Key 落盘。
- 审批指纹必须基于原始规范化载荷计算；如果先脱敏再哈希，不同 Secret 可能产生同一指纹。
- 客户端的 `confirmed: true` 不是授权，服务端必须验证审批状态、操作类型、指纹、session 和过期时间。

## 数据迁移先保护源数据

- SQLite 成为权威写入源前，先复制旧 JSON/JSONL 到带时间戳的备份目录。
- migration 与 legacy import 都要幂等；失败时回滚事务并保留旧文件。
- 不做长期双写，否则数据库和 JSON 很快会出现两个互相矛盾的真相。

## 调度不能绕过权限模型

- Cron 触发不等于用户授权，敏感执行必须进入 `waiting_approval`。
- 同一计划需要互斥，避免慢任务跨周期重入。
- 服务停机期间错过的触发应明确记录为 `skipped`，不能在重启时形成补跑风暴。

## Windows 后台部署

- 当前 PowerShell 进程可能同时含有 `Path` 和 `PATH`，`Start-Process` 会因环境字典键冲突失败；启动前应规范化为单一 `Path`。
- 部分沙箱会在命令结束时回收子进程；验收时应使用持续持有的服务会话，而不是仅凭启动日志判断服务仍在线。

## 审批界面必须解释能力边界

- `agent.dispatch`、`medium` 和原始 payload 是实现细节，不能替代用户需要的风险说明。
- 审批前应先计算真实执行范围，展示任务数量、筛选范围、Agent 选择策略，以及批准后开放的能力。
- 对外部 Agent CLI 的准确表述是“允许 myteam 启动 CLI”；CLI 内部是否读写文件、执行命令或联网，取决于任务内容和 CLI 自身权限，不能伪装成 myteam 已逐项审批。
- 拒绝路径也必须做闭环验证：审批应落为 `denied`，前端退出运行态，且不能启动新的任务执行。

## 流式反馈不能只解析最终正文

- Kimi 0.14 的 `stream-json` 会把 `tool_calls`、`role=tool` 和最终 `content` 分成独立 NDJSON 事件；只解析正文会让工具执行期间看起来一直卡在“正在思考”。
- 参考 LobsterAI，把思考、工具调用和最终正文作为三类独立可渲染事件：思考在流式期间默认展开，工具调用展示开始与完成，只有完全没有事件时才使用等待占位。
- dispatch 已经展示完整流式正文时，不应再追加内容相同的结果卡；任务状态应由任务列表和轻量完成状态承担。
- 网络流断开不等于 Agent 失败，错误文案要提示任务可能仍在后台运行，并给出刷新恢复路径。
- CLI 尚未发出任何事件时只能显示中性的“运行中/等待首个事件”，不能把静默期描述为模型“正在思考”；收到真实 thinking 或 tool 事件后应立刻由真实事件接管占位。

## 创建流程必须在提交前形成可用配置

- “从零创建”如果不同时收集 CLI 路径和启动参数，只会生成不可启动对象；不完整的模式应移除，而不是把修复责任留到创建后的设置卡。
- 变体创建要明确区分自动继承项与用户覆盖项，并在当前表单解释模型 ID、API 地址、API Key 分别何时需要填写。
- 密钥继承应由服务端根据基础对象完成，前端不应拿到明文再复制。
- 高频主操作应位于列表顶部；把“新建对话”放在滚动列表底部，会让历史越多、入口越难找。
