# myteamOUO 面试准备手册

## 60 秒项目介绍

myteamOUO 是我独立定义并通过 AI 辅助开发完成的本地多 Agent 协作控制台。我发现同时使用 Codex、Claude Code、Kimi 时，用户实际上要承担路由、复制上下文、追进度和验收结果的管理成本；一旦任务中断，还要重新解释背景。本项目把多个本机 Agent 串成“目标拆解—分工执行—跨模型审查—返工—经验沉淀”的闭环，并通过 SQLite 保存状态，通过审批、操作指纹和脱敏审计控制本地命令风险。我刻意没有直接复制 LobsterAI 的 Electron/OpenClaw 运行时或 Clowder AI 的完整平台，而是用单 Node 服务先验证轻量、本地优先的协作价值。目前已形成可运行 MVP，关键链路 22 项自动化测试全部通过。这个项目最能体现我的能力，不是我会堆多少 AI 功能，而是我能从真实痛点出发，做竞品判断、技术取舍、交互设计和验收闭环。

## 3 分钟展开结构

按这五步讲，不要从文件结构开始：

1. **场景：** 多个 Agent 各自很强，但用户仍在手工搬运上下文和管理流程。
2. **目标：** 让人只负责目标、关键决策和最终验收，系统负责协作过程。
3. **方案：** 结构化任务、Agent 分配、连续上下文、Reviewer Gate、安全审批、状态恢复。
4. **取舍：** 先做单 Node 服务和本机 CLI Adapter，暂不承担完整桌面运行时与生态复杂度。
5. **验证：** 可运行 MVP、22 项关键测试、真实中断恢复与多 CLI 接入；下一步补用户侧指标。

## 高频问题与参考回答

### 1. 这个项目到底解决了什么问题？

**回答主线：** 单 Agent 的问题是能力，多个 Agent 的问题是协作成本。用户会变成“人工路由器”：重复解释、复制上下文、安排分工、检查结果。myteamOUO 解决的是这层管理负担，同时让执行过程可审查、可恢复、可审计。

**追问准备：** 不要只说“提高效率”，要分别说明减少了哪些动作，以及准备用“首次成功时间、人工搬运次数、任务成功率、返工率”验证。

### 2. 目标用户是谁？为什么不是所有人？

**参考回答：** 第一阶段用户是已经同时使用两个以上本地 Agent CLI、会处理代码或复杂知识任务的个人开发者和 AI 重度用户。他们已经感受到上下文搬运和长任务管理成本，也能接受本地配置。普通办公用户更看重开箱即用，那是 LobsterAI 更擅长的方向，不应在 MVP 阶段同时争夺。

### 3. 和直接打开三个终端有什么区别？

**参考回答：** 终端只能提供单次执行，myteamOUO 增加的是协作状态：统一任务对象、负责人、验收标准、交接上下文、Reviewer Gate、审批记录和中断恢复。价值不在“能调用三个模型”，而在多次调用组成了一条可管理的任务链。

### 4. 为什么坚持本地优先？

**参考回答：** 项目和命令执行天然涉及源代码、本机路径和账号配置。本地优先能减少额外的数据外传面，也能复用用户已经登录的 CLI。但“本地”不等于“天然安全”，所以仍然需要权限分级、审批、审计和路径边界。

### 5. 为什么不用 LangGraph？

**参考回答：** LangGraph 适合复杂、持久、可回放的工作流，但 MVP 的核心风险不是图引擎能力不足，而是用户是否真的需要协作控制层。过早引入会增加模型 Provider、状态图和调试成本。我先用清晰状态机验证闭环；当分支、并行、补偿和长时工作流复杂度超过自研状态机时，再迁移到图运行时。

### 6. 为什么不用 Electron/OpenClaw？

**参考回答：** 它们能带来桌面权限、安装包和完整 Agent 运行时，但也会改变项目边界。我的优先级是用最小技术体量验证协作闭环，因此选择单 Node 服务和浏览器 UI。后续如果用户验证表明“一键安装和系统集成”是核心瓶颈，再补桌面壳或独立安装器。

### 7. 任务怎么分给不同 Agent？

**参考回答：** 当前先把目标结构化为 3–7 个任务，每个任务包含负责人、原因、步骤、取舍和验收标准，再根据可启动 Agent 与角色配置分配；服务端会校验并在 Agent 不可用时回退。下一步会把路由从静态能力标签升级为基于历史成功率、成本和任务类型的策略。

### 8. 如何避免 Agent 交接时丢上下文？

**参考回答：** 我没有全量重放历史，而是分三层：Continuity Capsule 保存目标、约束、决策、失败和下一步；Top-K Evidence 找最相关的历史证据；Workspace Bridge 注入当前 Git 状态和改动。这样既保留关键事实，也控制上下文噪声。

### 9. Reviewer Gate 为什么有价值？会不会只是多调用一次模型？

**参考回答：** Gate 的关键不是“再问一次”，而是审查者拿到独立角色、明确验收标准和执行证据，并能输出通过或返工状态。当前是人机结合的显式 Gate，避免早期把不可靠判断全自动化。下一步会记录审查命中率与返工收益，证明额外成本是否值得。

### 10. 安全是怎么做的？

**参考回答：** 服务端对 Shell、Skill 安装、配置写入和任务执行统一做风险分类；敏感操作生成审批对象，并对原始载荷做指纹，批准后若内容变化就拒绝；审批支持单次和会话级，审计自动脱敏秘密信息。边界也要诚实：目前只能控制 myteam 管理的入口，不能逐项拦截外部 CLI 内部工具。

### 11. 为什么要设计中断状态机？

**参考回答：** 早期“点击停止后立刻允许继续”会产生竞态：旧进程的关闭回调可能把输出写进新任务。后来改为 `running → interrupting → interrupted → running`，先等待旧进程收口，再开放恢复入口。这个改动体现了产品状态与后端执行状态必须一致。

### 12. 项目中最难的产品决策是什么？

**参考回答：** 最难的是克制功能范围。竞品都有桌面端、MCP、IM、多场景能力，很容易变成追功能。我最终选择把差异点收敛为“轻量、本地、透明的多 Agent 协作闭环”，优先做上下文、审查、安全和恢复，因为这些直接决定复杂任务能否放心交给系统。

### 13. 你怎么证明这个产品有价值？

**参考回答：** 当前证明的是“方案可行”，还不是“市场成立”：关键链路已运行并有 22 项测试，但缺真实用户数据。下一阶段会招募 5–10 名已有多 Agent 使用习惯的用户，完成统一基准任务，对比手工多终端与 myteamOUO 的完成时长、上下文搬运次数、人工介入、返工率和主观信任度。

### 14. 你如何做优先级？

**参考回答：** 用“用户价值 × 风险降低 × 验证成本”判断。结构化计划、恢复和审批既影响核心体验又降低失败风险，所以优先；语音、IM、多媒体生成虽然显眼，但不能验证核心协作假设，所以后置。

### 15. 你使用 AI Coding，如何证明不是模型替你做的？

**参考回答：** 我会明确承认使用 Codex、Claude Code 辅助实现。我的职责是定义问题、拆解需求、做竞品与架构取舍、规定验收标准、判断实现是否符合产品语义，并通过测试和真实交互验收。AI 降低了编码成本，但“做什么、为什么做、什么算完成、哪里不能做”仍由我负责。仓库中的决策文档、问题复盘和迭代历史可以证明这一点。

### 16. 项目失败或返工最多的地方是什么？

**参考回答：** 典型问题包括 CLI 参数兼容、结构化 JSON 混入用户正文、实时事件与历史回放语义不一致，以及中断恢复竞态。共同教训是：多 Agent 产品不能只把输出展示出来，必须先定义稳定的领域对象、事件契约和状态机。

### 17. 和 LobsterAI 的差异是什么？

**参考回答：** LobsterAI 更像面向大众办公场景的桌面级全能 Agent，强项是 OpenClaw 运行时、丰富 Skills、MCP、IM 和安装分发。myteamOUO 更轻，强调复用现有 CLI 和显式协作治理。短期不应和它拼全场景，而应把“多模型任务协作的透明性和低部署成本”做深。

### 18. 和 Clowder AI 的差异是什么？

**参考回答：** Clowder AI 更强调持久身份、团队文化、共享记忆、跨模型审查和 Mission Hub，是完整的多 Agent 平台。myteamOUO 当前是更小的控制台原型。值得学习的是治理和协作纪律，但我的产品应避免复制其体量，先把单人复杂任务的可验证协作做成清晰样板。

### 19. 如果只能再做一个功能，你做什么？

**参考回答：** 我会做“可量化的任务实验与回放”，而不是再接一个模型。它记录任务阶段、人工介入、上下文来源、耗时、成本、审查与返工结果，让我能判断协作是否真的优于手工多终端，并为后续路由策略提供数据。

### 20. 这个项目怎么商业化？

**参考回答：** 先不急着按模型调用收费，因为模型账号由用户持有。更合理的方向是免费本地核心 + 专业版协作治理能力，例如团队策略模板、任务回放、成本与质量分析、私有 Skill 管理和企业审计。商业化前提仍是先验证个人用户的高频任务与留存。

## 面试官可能继续深挖的技术问题

| 问题 | 回答关键词 |
|---|---|
| 为什么使用 SQLite WAL？ | 本地单机、事务、并发读、迁移、崩溃恢复 |
| SSE 和 WebSocket 如何选择？ | 当前主要是服务端流式推送，SSE 简单；双向高频协作再评估 WebSocket |
| 如何防止 Agent 循环派生？ | 最大深度、链路历史、A/B 交替模式检测、人工接管 |
| 如何保证审批后命令没被换掉？ | 规范化载荷 + 服务端指纹 + 决策时重新校验 |
| 为什么 Top-K 不是完整 RAG？ | 当前是关键词证据检索；缺 embedding、引用、更新和遗忘机制 |
| 为什么测试数量不多？ | 优先覆盖高风险状态与契约；下一步补 API、端到端和基准任务 |

## 反问面试官

- 团队目前在 AI 产品中最关注的是能力上限、交付稳定性，还是用户信任？
- 产品策划在贵团队是否直接参与 Prompt、数据口径和模型效果验收？
- 当前 AI 功能从 Demo 到正式上线，最常见的阻塞点是什么？
- 团队如何定义 AI 功能“可上线”：离线评测、线上指标与人工审核分别占多大权重？

## 回答纪律

- 明确区分“已经实现”“本地验证”“计划做”三种状态。
- 业务数据说明口径，不把相关性直接说成严格因果。
- 承认 AI 辅助开发，不弱化自己的产品决策与验收责任。
- 每个回答先讲结论，再讲一个证据，最后讲边界或下一步。
